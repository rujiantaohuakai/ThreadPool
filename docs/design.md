# ThreadPool Design

## 项目目标

本项目实现一个基于 C++17 的固定大小线程池，目标是提供一个可复用、线程安全、易于理解的并发基础组件。

当前版本聚焦第一阶段能力：

- 固定数量工作线程
- 线程安全任务队列
- 条件变量阻塞等待
- 支持任意可调用对象提交
- 支持 `future` 获取任务结果
- 支持优雅关闭

## 核心类设计

当前线程池类名为 `ThreadPool`，主要职责包括：

- 创建并管理工作线程
- 维护任务队列
- 负责线程同步
- 提供任务提交接口
- 控制线程池关闭和资源回收

核心成员：

- `workers`
  保存所有工作线程
- `taskque`
  保存待执行任务，类型为 `std::queue<std::function<void()>>`
- `mtx`
  保护任务队列和停止标志
- `cv`
  在无任务时阻塞工作线程，在新任务到来或关闭时唤醒
- `isstop`
  表示线程池是否已停止

## 线程模型

线程池在构造时接收线程数 `threadNums`：

1. 校验线程数必须大于 0
2. 创建固定数量工作线程
3. 每个工作线程启动后进入 `worker` 循环

每个工作线程的执行逻辑如下：

1. 获取锁
2. 使用条件变量等待，直到：
   - 线程池停止，或
   - 任务队列非空
3. 如果线程池已停止且任务队列为空，退出线程
4. 否则从队列取出一个任务
5. 释放锁
6. 执行任务
7. 继续下一轮循环

这个模型保证：

- 无任务时线程不会忙等
- 执行任务时不长期持锁
- 多个工作线程可以并发执行不同任务

## 任务提交设计

任务提交接口为模板函数 `enqueue`，放在头文件中实现。

这样设计的原因是：

- 模板函数需要在使用点可见，避免链接问题
- 返回值类型需要依赖模板参数推导

任务提交流程：

1. 使用 `std::invoke_result` 推导任务返回值类型
2. 使用 `std::packaged_task` 封装任务
3. 通过 `get_future()` 获取对应的 `std::future`
4. 将任务再包装为 `std::function<void()>`
5. 加锁后放入 `taskque`
6. 通知一个工作线程执行任务
7. 返回 `future` 给调用方

这样做的好处是：

- 工作线程不需要关心返回值类型
- 调用者可以通过 `future.get()` 获取结果或异常
- 接口同时支持有返回值和无返回值任务

## 关闭策略

关闭接口为 `shutdown()`，析构函数中也会调用它。

当前关闭策略是：

- 停止接收新任务
- 已提交任务继续执行
- 队列清空后工作线程退出
- 主线程等待所有工作线程 `join`

关闭流程：

1. 加锁检查 `isstop`
2. 如果已经停止，直接返回
3. 否则将 `isstop` 设为 `true`
4. `notify_all()` 唤醒所有等待线程
5. 对所有可联结线程执行 `join`

这种策略属于“优雅关闭”，适合线程池基础版本。

## 线程安全策略

共享状态主要有两类：

- `taskque`
- `isstop`

它们都由同一把互斥锁 `mtx` 保护。

线程安全策略要点：

- 入队时加锁
- 出队时加锁
- 检查停止标志时加锁
- 执行任务时释放锁
- 条件变量使用谓词等待，避免虚假唤醒导致错误逻辑

## 异常处理策略

当前异常处理规则如下：

- 如果构造函数收到 `threadNums == 0`，抛出 `std::invalid_argument`
- 如果线程池已经停止，再调用 `enqueue`，抛出 `std::runtime_error`
- 如果任务内部抛出异常，异常由 `std::packaged_task` 传递到 `future`

这种设计的好处是：

- 线程池本身的错误能被及时发现
- 任务执行错误不会破坏线程池整体结构
- 调用者可以在 `future.get()` 时显式处理异常

## Demo 与 Test 的职责

当前项目中：

- `src/main.cpp`
  用于演示线程池的使用方式，包括提交任务、打印线程 ID、获取结果
- `test/test_thread_pool.cpp`
  用于验证线程池行为是否正确

测试目前覆盖：

- 基础任务执行
- `future` 返回值
- `shutdown` 后拒绝提交
- 大量任务提交后正常退出
